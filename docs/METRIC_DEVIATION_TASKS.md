# Переход «отклонение показателя → задача ответственному»

Реализует ключевое звено управленческого цикла ТЗ v2.12: достоверные данные →
отклонение KPI → фокус руководителя → задача ответственному.

## Что сделано

Миграция `021_metric_deviation_tasks.sql` (аддитивная, с ledger):

- таблица `metric_deviation_tasks` — неизменяемая связь задачи с основанием:
  филиал, показатель, период, `snapshot_id` (версия опубликованного значения),
  `threshold_id` (версия порога), зафиксированные `rag`, `observed_value`,
  `basis`, `basis_value`, обязательное основание 16–500 символов, автор, `audit_id`;
- ограничение уникальности `(филиал, показатель, период, snapshot_id, threshold_id)` —
  одно и то же отклонение при той же версии порога не порождает дубли задач;
  новая версия порога или новая ревизия публикации — новое основание;
- триггер append-only: изменить или удалить основание задачи нельзя;
- типы агрегата `metric_deviation` в `audit_log` и `outbox_events`;
- событие `metric.deviation.task_created` с политикой уведомлений `NONE`.

Сервер `src/metrics/deviationTasks.ts`:

- `POST /api/v1/metrics/deviation-tasks` — постановка задачи по отклонению.
  Статус клиента не является основанием: сервер заново читает опубликованное
  значение из `report_fact_current`/`report_fact_snapshots`, действующий порог
  через `resolveThresholds`/`thresholdFor` и пересчитывает статус `evaluateRag`.
  Задача создаётся только при `RED` или `AMBER`;
- отказы с кодом `DEVIATION_CONFLICT` (409): порог не настроен, отклонения нет,
  статус изменился, значение переопубликовано (устаревший `snapshot_id`),
  задача по этому отклонению уже поставлена — в деталях возвращается
  `work_item_id`, чтобы был переход к существующей задаче вместо дубля;
- задача создаётся штатным `workItemService.createWorkItem` — сохраняются
  проверки прав РМ, допуска филиала к новым задачам, шаблона, идемпотентности,
  аудита и outbox; шаблон задачи задаётся в команде, а не в коде;
- необязательное назначение ответственного через `assignWorkItem` с проверкой
  роли-владельца шаблона; без назначения задача остаётся в статусе `DRAFT`;
- `GET /api/v1/metrics/deviation-tasks?start&end[&org]` — перечень поставленных
  задач в пределах допусков пользователя к показателям.

Сетка филиалов (`src/metrics/overview.ts`) теперь возвращает `snapshot_id` и
связанную задачу по каждой ячейке; календарная проверка даты приведена к
строгой форме (31.02 отклоняется как 422, а не подменяется соседней датой).

Клиент: `components/deviationTaskModel.ts` (чистая логика: доступность перехода,
название по умолчанию, перевод срока из московской даты в UTC, предпроверка
черновика), `components/DeviationTaskModal.tsx`, действие «Создать задачу по
отклонению» в `BranchGrid` только для красных и жёлтых ячеек с настроенным
порогом, ссылка на уже поставленную задачу и её статус.

## Ограничения, заявленные честно

- Ответственный не подставляется автоматически: исполнитель должен иметь роль,
  которую шаблон называет владельцем полей, поэтому назначение выполняется в
  карточке задачи или передаётся явно в команде.
- Отсутствие значения или порога — это «Нет данных», а не ноль: задача в этом
  случае не создаётся.
- Уведомление ответственному при назначении идёт штатным событием
  `work_item.assigned`; отдельной рассылки по отклонениям не добавлено.

## Тесты

- `server/test/metricDeviationTasks.ts` — 24 теста: сессия, Origin, CSRF,
  Idempotency-Key, 17 некорректных команд, проверка отклонения на сервере,
  запрет дублей, неизменяемость связи, зелёный статус и отсутствие порога,
  устаревшая версия снимка, изоляция по допускам, назначение ответственного,
  отображение в сетке и перечне.
- Полная регрессия: серверный прогон 139 тестов, изолированные наборы 276
  тестов, клиент 56 тестов, сборки клиента и сервера без ошибок.
