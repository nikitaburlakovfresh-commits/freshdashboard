# FRESH Portal: личные задачи ролей и подготовка beta

## Границы выпуска

Локальный выпуск поверх c4833515. Production, GitHub и реальные права в этом этапе не изменяются. Действует решение пользователя «Продолжить без установки».

Утверждённое архитектурное решение: собственный сервер является основным хранилищем нового портала. Яндекс Диск используется временно для переноса и сверки, не как обязательный посредник текущих записей. Эта запись решения не означает, что закончены перенос старых файлов, резервное копирование вне основного сервера или проверка восстановления.

Уточнение пользователя имеет приоритет над старым порталом и прежним обзором: совместного заполняемого ежедневника филиала не будет. Роли имеют отдельные формы и персонального исполнителя. Руководитель проверяет результаты в пределах действующих полномочий.

## Реализованный объём

- Каталог неизменяемых шаблонов для постановщика РМ. Шаблон определяет ровно одну роль исполнителя.
- Карточка получает всю закреплённую схему, а не только первое текстовое поле.
- Интерфейс текста, чисел, ссылок, дат, выбора и повторяемых записей. Поля сохраняются на сервере по одному с проверкой версии. Сдача фиксирует единый снимок всех полей.
- Сохранение одного поля не стирает несохранённые соседние поля и не обновляет их исходную версию без согласия. Ошибка конфликта не заменяет ввод серверным значением.
- Личный список назначенных, выполняемых и сданных задач с фильтром точной роли и текущих назначений филиала. Смена даты не создаёт копию, не изменяет срок и не закрывает задачу.
- Сервер возвращает текущую московскую дату. Интерфейс предупреждает о смене даты без автоматической перезагрузки.
- Добавлены два общих шаблона личных поручений РОП и РОО. Они не являются полным ролевым ежедневником.
- Создание срока и отображение карточки используют Москву, UTC+3.

Существующие пять RF-форм из миграции 008 остаются предварительными: их происхождение и ограничения описаны в самой миграции. Ручные значения не публикуются как KPI, вычисляемые поля ещё требуют утверждённых формул. Разделы с неподтверждённым обещанием дополнительной видимости из старых скриншотов не выводятся как права доступа.

## Что не закрыто

- Полный персональный ежедневник с business_date, датированными записями и окнами заполнения.
- Регулярная генерация и связь снимка результата задачи с выбранным днём ежедневника по §13.14 ТЗ.
- Полные формы и согласованные вычисления для всех ролей.
- Миграция старых данных и утверждённое сопоставление пользователей и филиалов.
- Публикация проверенных KPI, планов и карточка филиала с их историей.
- Полный конструктор шаблонов без кода, offline и восстановление ввода между устройствами.

Личный список на странице «Ежедневник» явно обозначен первым рабочим сценарием beta, а не завершённым дневным отчётом. Нельзя снимать статус разработки со всего модуля.

## Проверки

Серверные наборы запускаются отдельно: общий набор 125; назначения 26; активация 19; подключение пользователей 20; canonical scope 10; редактор структуры 27; загрузки 40; черновики проверок 31. Всего 298. Клиентские проверки: 48.

Первый общий запуск административных наборов в одном процессе был некорректен: наборы предполагают отдельную очистку синтетической базы. Повторная проверка выполнена отдельными независимыми запусками. Исправлены ошибка новой миграции (обязательный UUID шаблона) и ошибочное ожидание формы ответа в новом тесте. Применённые прежние миграции не редактировались.

### Браузерная приёмка

- РМ: выбор шаблона/роли, создание со сроком МСК, назначение подходящего исполнителя.
- РФ: заполнение всех числовых полей и повторяемой группы, добавление и удаление записи, сохранение и сдача.
- Несохранённые соседние поля остаются после сохранения одного; статус не меняется до сохранения.
- Невалидная ссылка/число: серверная ошибка, введённые значения не потеряны.
- РМ: чтение всех результатов, возврат с причиной, повторная сдача и принятие.
- Личный список: переключение RF/ROP, принятая задача исчезает из открытых, исходная карточка и история остаются.
- Смена дня: уведомление без принудительного перехода. Контрольный автоматизированный тест времени браузера.
- Светлая и тёмная темы; desktop 1440×1000 и mobile 390×844; отсутствие горизонтального переполнения.

Проверено фактически: создание и назначение формы РФ; все числовые поля и повторяемая группа; сохранность соседнего несохранённого поля; добавление/удаление строки; отклонение неверной ссылки без потери текста; сдача → возврат с причиной → исправление → повторная сдача → принятие. Принятый экземпляр остаётся доступен с историей, но исчезает из открытых.

Отдельно созданы и назначены синтетические поручения РФ/РОП/РОО. Роли переключены в личном списке; у РОП выполнены сохранение, начало и сдача; у РОО сохранён собственный результат. Проверено отключение смены статуса при несохранённом вводе. Управляемые часы браузера подтверждают предупреждение после московской полуночи без исчезновения открытой задачи.

Снимки светлой/тёмной тем просмотрены; ширина документа на мобильном экране равна 390 px при viewport 390 px. Ошибок JavaScript в проверенных сценариях нет. Контроль даты и select в схеме покрыт серверными тестами; отдельная ручная браузерная приёмка каждого такого шаблона не заявляется. Offline, восстановление ввода после закрытия вкладки и нагрузка не проверялись и не входят в готовый объём.

## Минимальная beta для собственника

Первый показ следует ограничить одним подтверждённым филиалом и личными ролями РМ/РФ/РОП/РОО. Показать создание и выполнение задачи, проверку, сохранение истории и разделение доступа. Отдельно обозначить ещё не принятые части ежедневника и KPI.

До реальной beta нужны согласованные ФИО/логины и назначения, дата действия структуры, согласие на установку накопленного выпуска, резервная копия и репетиция на копии production, проверка прав и входа. Рабочие метрики требуют подтверждённых периода, формул и источников; отсутствие значения не заменяется нулём.

Следующая разработка: датированные персональные записи ежедневника и привязка снимков результатов задач; затем одна проверенная цепочка загрузка → проверка → публикация KPI → карточка филиала. Старый портал остаётся источником сверки до приёмки, не источником бизнес-логики.
