# Уведомление ответственному при назначении задачи по отклонению

Инкремент управленческого цикла ТЗ v2.12: после шага «отклонение → задача ответственному»
ответственный получает уведомление внутри портала, а политика рассылки настраивается
внутри портала, а не в коде.

## Что реализовано

### Доставка уведомления
- Уведомление доставляется штатным событием назначения задачи `work_item.assigned`
  через существующий потребитель `in_app_v1` (outbox → consumer → `notifications`).
  Поэтому оно срабатывает и при постановке задачи по отклонению сразу с ответственным,
  и при последующем переназначении задачи другому руководителю.
- Если задача связана с отклонением (`metric_deviation_tasks.work_item_id`), текст
  уведомления — «Вам назначена задача по отклонению показателя.» Обычная задача
  сохраняет прежний текст «Вам назначена задача.»
- Отдельные тексты предусмотрены также для возврата на доработку и возобновления
  задачи по отклонению.
- Текст шаблонный: значения показателя, порога и период в уведомление не попадают.
  Цифры остаются доступны только на экранах с проверкой допуска к показателям
  (`report_fact_access`). Это сознательно, чтобы уведомление не стало обходным
  каналом раскрытия бизнес-данных.
- Получатель перепроверяется в момент обработки события: нужна активная учётная
  запись и действующий role grant роли-владельца шаблона в этом филиале. Отозванный
  доступ даёт запись `SKIPPED_ACCESS_REVOKED`, а не уведомление.
- Постановщик не уведомляет сам себя.
- Событие фиксации отклонения `metric.deviation.task_created` остаётся доказательным
  и рассылку не порождает: иначе при постановке задачи с ответственным приходило бы
  два уведомления об одном действии.

### Настраиваемость политики рассылки
- Политика по каждому событию читается из таблицы `event_catalog.notification_policy`
  (`NONE` | `ASSIGNEE` | `REVIEWERS`). Карта в коде осталась только резервом для
  события, которого ещё нет в каталоге.
- `GET /api/v1/metrics/notification-policies` — текущие политики всех событий,
  допустимые значения и последние 200 изменений.
- `POST /api/v1/metrics/notification-policies` — изменение политики. Требует право
  `notification.policy.manage`, `Idempotency-Key` и основание 16–500 символов.
  Неизвестное событие — 404, недопустимое значение — 422, отсутствие права — 403.
- Миграция `022_notification_policies.sql` (additive): право
  `notification.policy.manage`, событие `notification.policy.changed`,
  append-only таблица истории `notification_policy_changes` с триггером,
  запрещающим UPDATE и DELETE. Каждое изменение связано с записью аудита
  (`retention_class = SECURITY_5Y`).
- Изменение политики применяется к ещё не обработанным событиям; уже созданные
  уведомления не переписываются и не удаляются.

## Тесты
Новый изолированный набор `server/test/deviationNotification.ts` — 6 тестов на
реальном PostgreSQL, только синтетические филиалы, пользователи и значения:

| Тест | Проверяет |
|---|---|
| ND-01 | ответственный получает уведомление о задаче по отклонению; цифр в тексте нет; постановщик себе не уведомляет |
| ND-02 | при переназначении уведомление приходит новому ответственному |
| ND-03 | политика берётся из настроек: `NONE` отключает рассылку, но доказательный след события сохраняется |
| ND-04 | изменение политики требует права, основания и известного события |
| ND-05 | история изменений сохраняется и защищена от перезаписи на уровне БД |
| ND-06 | обычная задача сохраняет прежний общий текст |

Регрессия: серверный прогон 139 тестов, изолированные наборы 300, клиент 62,
типизация сервера и клиента чистая, сборка клиента успешна.

## Расхождения и ограничения
- Порог «срок близко» на экране «Мои задачи по отклонениям» (72 часа) по-прежнему
  задан в коде и не выведен в настройки портала.
- Канал доставки только `IN_APP`. Почтовая и мессенджер-рассылка в этом инкременте
  не реализованы: для них нужен отдельный потребитель и согласование политики
  внешних каналов.
- Интерфейс настройки политики пока только API; отдельный экран администратора
  в этом инкременте не добавлен.
