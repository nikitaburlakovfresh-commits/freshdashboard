# FRESH Portal: управление допусками к метрикам

## Граница выпуска

Добавлена страница `/access/metrics`, доступная из существующего раздела
пользователей. Она управляет явными READ/PUBLISH-допусками существующих
назначений, но не создаёт роли, пользователей или сетевые области видимости.
Финансовые значения, задачи и ежедневники при изменении допуска не меняются.

Миграция 018 добавляет каталог `report.fact_access.manage`, неизменяемые
проверки и квитанции. **Никаких автоматических выдач разрешений нет.**
Миграция 017 не изменена.

## Полномочия и первичное включение

Каждый запрос проверяет живую личную сессию и явные действующие NETWORK-права
`access.directory.read` + `report.fact_access.manage`. Название роли не заменяет
эти проверки. POST также проверяет Origin, CSRF и лимит запросов.

Для первоначального, отдельно согласованного включения предусмотрена команда:

```text
node server/dist/scripts/provisionFactAdministrator.js <bootstrap-login> <approval-reference>
```

Команда принимает только существующего единственного личного
bootstrap-администратора с правом справочника. Изменение аудитируется;
повтор не выдаёт разрешение заново, а несоответствие журналу блокируется.
Ни запуск приложения, ни HTTP-запрос её не вызывают.

После первичной настройки обычные допуски сотрудникам выдаются/отзываются
через интерфейс, без операторских команд. Управление самой моделью
административных полномочий и полномасштабный редактор ролей этим не заменены.

Самовыдача и самоотзыв на этой странице запрещены. Публикация дополнительно
требует уже существующего bootstrap/SUPER_ADMIN и staging на весь срок.
При единственном администраторе это означает, что его первоначальный PUBLISH
по-прежнему потребует отдельно одобренной операторской настройки; интерфейс
не создаёт второго сетевого администратора и не обходит запрет самовыдачи.

## Жизненный цикл

1. Выбор существующего назначения, READ/PUBLISH, метрик и основания.
2. Начало NOW или будущая точная дата; окончание в пределах назначения.
   Для чтения нужен активный реальный филиал, не пилотные A/B.
3. Серверная проверка без изменения допуска: actor, целевая учётная запись,
   назначение, филиал, прежний допуск и staging фиксируются хешем.
4. Preview действует 10 минут. Проверка и подтверждение не взаимозаменяемы.
5. Применение повторно проверяет текущие полномочия, состояние и срок.
   UUID проверки служит ключом идемпотентности; повтор той же проверки
   возвращает квитанцию только после повторной авторизации.
6. Допуск, аудит, событие и квитанция записываются одной транзакцией.

Действующий допуск нельзя перезаписать. Для изменения метрик требуется
отдельный отзыв, затем новая выдача: это явно видимые два действия и возможный
промежуток без доступа. Отозванный/завершённый допуск допускает новую выдачу
с сохранением before/after в неизменяемом аудите. Будущая выдача пока не активна.
Отзыв немедленный, в том числе для неактивного целевого пользователя.

Исторические факты не редактируются. Чтение исторических фактов подчиняется
текущему доступу; это не историческое воспроизведение ранее выданных прав.
UI показывает последние 100 изменений; полный журнал остаётся в PostgreSQL.
Каталоги свыше 5000 записей блокируются явно, а не обрезаются молча.

## Следующий барьер перед production

Этот код не установлен. Необходимы:

- реальное AV-окружение и обновление сигнатур, тест отказов без обходов;
- согласованный состав накопленного выпуска, миграции, backup/restore rehearsal
  и откат; локальные миграции не заменяют проверку на копии боевой схемы;
- точные первоначальные пользователи/назначения/филиалы/метрики и основания,
  первичное право администратора отдельно от его собственного PUBLISH;
- явное сообщение о готовности кандидата и отдельное разрешение пользователя
  на production-деплой. Продолжение разработки таким разрешением не является.
