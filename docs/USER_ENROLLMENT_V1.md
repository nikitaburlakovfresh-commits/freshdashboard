# FRESH Portal: личные пользователи и первый вход

## Границы выпуска

Локальная реализация поверх 664c49d. Решение «Продолжить без установки» сохраняется: production не изменён, реальные люди не заведены, права не выданы, сообщения не отправлены.

ТЗ v2.12: §3.8 требует персональную идентичность и primary_email; §3.7 задаёт одноразовые ссылки с TTL 72 часа. Реализовано только первоначальное подключение новой личной записи, не массовая ротация, не восстановление пароля действующего сотрудника и не миграция общих логинов.

## Реализованный путь

1. Администратор с NETWORK + `access.directory.read` + `user.create` вводит логин, ФИО, персональную рабочую почту и основание.
2. Подтверждает создание. Новая запись INDIVIDUAL неактивна; случайный неизвестный пароль, ноль ролей и сессий. Повтор одинакового запроса не создаёт дубль.
3. С отдельным `user.enrollment.manage` выпускает приглашение. Оно действительно 72 часа, показывается один раз и автоматически не отправляется.
4. Администратор проверяет адресата и передаёт секрет по утверждённому защищённому каналу. Записанная почта не считается автоматически верифицированной.
5. Сотрудник открывает `/activate-account#<секрет>` и задаёт уникальный пароль длиной 14–200 символов. Это политика данного ограниченного выпуска, не утверждение о полной корпоративной парольной политике.
6. Ссылка одноразово погашается, запись активируется. Сессия автоматически не создаётся, права не назначаются.
7. Обычный личный вход; администратор отдельно проводит черновик → проверку → применение роли на конкретный ACTIVE-филиал.

## Безопасность и согласованность

- Миграция 013 добавляет nullable primary_email старым записям без выдумывания адресов. Для нового пользователя почта обязательна в API. Case-insensitive уникальность логина и почты; существующие дубли останавливают миграцию, не объединяются автоматически.
- Миграция регистрирует два права, но никому их не выдаёт. Нужен отдельно согласованный аудируемый этап включения, не произвольные команды из UI.
- В базе приглашения хранятся только SHA-256 digest, срок и версия. Исходный bearer не попадает в audit, outbox или idempotency. Ссылки нет в GET-каталоге.
- В URL используется fragment, не query. Страница удаляет fragment из текущей записи истории. Пароль и bearer передаются только в POST. Для внешнего запуска обязателен HTTPS; на тестовом стенде только loopback.
- Выдача и отзыв защищены текущими правами, Origin, CSRF и expected_version. Повторный выпуск отменяет старую ссылку. Если ответ потерян, сначала обновляется справочник и выполняется явный новый выпуск, секрет не восстанавливается из журнала.
- Приём приглашения проверяет Origin, ограничение частоты и срок. Два одновременных приёма дают один успех. Состояние пользователя, версия приглашения, audit и outbox фиксируются атомарно.
- Существующий активный или ранее отключённый пользователь без записи первоначального подключения не может получить такой сброс пароля.
- Преждевременные grants/сессии у ожидающего пользователя блокируют выдачу и активацию. Дополнительные роли не наследуются автоматически.
- Ошибки чувствительных API логируются без тела запроса или полного PostgreSQL diagnostic.

## Ограничения перед production

Нет автоматической email/Telegram-доставки, верификации владения почтой, массового импорта людей, восстановления существующих паролей, MFA и группового переноса legacy. Текущий rate limiter однопроцессный; перед массовым запуском проверить reverse proxy, реальную IP-адресацию и общий лимитер. Для одиночного пилота права и адресат приглашения проверяются оператором.

Включение новых административных прав в production требует отдельного аудируемого согласования; этот выпуск не добавляет автоматически исполняемый provisioning. Реальные ФИО, логины, персональные адреса, роли, филиалы и даты назначений должны быть подтверждены владельцем сети.

## Инвентарь проверок

### Автоматические

- Анонимный/чужой scope/нет отдельного permission, Origin, CSRF.
- Строгие входные поля, email, логин, основание, дубли и повтор создания.
- Секрет выдаётся один раз, digest-only, TTL, no-store и отсутствие в журналах.
- Перевыпуск, отзыв, истечение, устаревшая версия, повторный и конкурентный приём.
- Откат при недоступном audit, существующие пользователи недоступны для переактивации.
- Новый РМ и РФ через первый вход + реальные по типу (синтетические по содержимому) филиалы + явные назначения + полный цикл задачи до COMPLETED; чужой филиал получает 404.
- Регрессия остальных модулей и клиентских моделей.

### Браузерная приёмка

- Создание: заполнение, подтверждение, отмена без создания, успешная запись.
- Приглашение: явный выпуск, скрытие ссылки, обновление, перевыпуск и отзыв.
- Публичный первый вход: очистка fragment, несовпадение паролей, успешная установка, повторный приём и обычный вход.
- Отсутствие права: нет рабочих административных команд.
- Карта модулей: частичная готовность, ссылки на существующие экраны, отсутствие обещаний полной готовности.
- Desktop 1440×1000 и mobile 390×844, обе темы, ошибки страницы и переполнение.
- Снимки не содержат действующих bearer-ссылок; поля ссылок маскируются.

Проверки выполнены локально: 20 новых серверных тестов и 270 регрессионных, всего 290; 43 клиентских теста. TypeScript/Vite build и повторный запуск миграций прошли. Это не репетиция на копии production.

Перечисленные браузерные сценарии пройдены на настоящем локальном API с синтетическими данными. Дополнительно проверено открытие новой ссылки в той же вкладке: старый секрет и введённые пароли очищаются. Исправлены обработка смены fragment и оформление кнопки первого входа. Ошибок страницы и горизонтального переполнения на проверенных размерах нет. Боевые данные и production не проверялись этим прогоном.
